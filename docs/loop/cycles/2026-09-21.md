## 오늘의 스코프

먼저 `docs/loop/backlog.md`에서 status가 "대기"이면서 source가 `human-added` 또는 `eval-found`인 항목이 있는지 확인했습니다. 정책 7항 및 갭 승격 기준상 사람이 등록했거나 평가에서 발견된 갭은 벤치마크 순회보다 우선 소비해야 하기 때문입니다. 검토 결과 B001~B015가 모두 "완료" 상태이며 "대기" 항목이 하나도 없어, benchmark-suite 고정 목록을 cursor 순서대로 소비합니다.

`docs/loop/benchmark-suite.md`의 frontmatter cursor 값은 7이고 표는 10개 행(BM01~BM10)이므로, 0-based 인덱스 7에 해당하는 **BM08 — Atlassian Statuspage 소개**(https://www.atlassian.com/software/statuspage, 패턴: 모니터링/상태)를 오늘의 벤치마크로 선택합니다. 직전 사이클(2026-09-17, BM07)에서 cursor를 7로 갱신했으므로 이번 사이클은 그 다음 항목을 이어서 처리합니다(정책 7항 회귀 순회). benchmark-suite 항목을 선택했으므로 `docs/loop/backlog.md`의 status는 변경하지 않으며, benchmark-suite의 cursor만 (7+1) % 10 = 8로 갱신했습니다.

BM08은 서비스 가동 상태(component status)와 진행 중/과거 인시던트, 예정된 점검(scheduled maintenance), 업타임 이력을 상태별 색상과 타임라인으로 진열하는 "모니터링/상태" 패턴에 해당합니다. 재현·평가 시 다음 정책 가드레일을 유의합니다.

- 정책 3항(축 분리): 이 패턴이 기간계(business/admin)와 일반 웹사이트(service) 중 어느 축에 해당하는지 먼저 판단하고, 그 축 안에서 이미 있는 패턴과 겹치지 않는 갭만 채택합니다. Statuspage는 외부 공개용 상태 페이지(service 축)와 내부 운영 모니터링 대시보드(business 축)의 성격을 함께 가지므로, 어느 축으로 재현할지 먼저 확정한 뒤 그 축 안의 기존 패턴과 대조합니다. 두 축을 뒤섞은 패턴은 채택하지 않습니다.
- 정책 2항 및 2-1항(중복 금지·구조 대조 의무화): 신규 작업에 앞서 `src/components/`·`src/templates/`의 기존 모니터링/상태·대시보드 계열 자산(StatusBadge, ActivityTimeline(B003), Calendar/Schedule(B004), 대시보드 템플릿, Card/Grid/Tag/ColorTag/Divider/Stat 계열 등)을 반드시 Read해 목적·props 구조가 겹치는지 확인한 근거를 남긴 뒤에만 추가 범위를 확정합니다. 같은 범주(상태 표시·타임라인·업타임 이력)로 판단되는 기존 템플릿이 있으면 신규 파일을 만들지 않고 기존 템플릿에 prop을 확장하는 방식으로만 처리합니다.
- 정책 8항(갭 승격 기준): 발견된 부족 항목을 design-system-gap(구조적 부재)과 execution-issue(실행 품질 이슈)로 구분해, design-system-gap으로 판정된 경우에만 컴포넌트/토큰을 추가하고 execution-issue는 시스템을 변경하지 않고 리포트에만 기록합니다.
- 정책 9항(일관성 유지): 업그레이드가 필요하더라도 전체 컨셉·스타일을 유지하는 범위 내 추가만 허용하며, 기존 시맨틱 토큰 체계 밖의 색상값 하드코딩이나 새로운 스타일링 체계 도입은 금지합니다.
- 정책 5항(병합 게이트): 모든 변경은 `develop` 대상 PR로만 제출하며, `main`/`develop` 직접 push는 금지합니다.

## 구조 대조 (정책 2-1항)

`src/templates/business/`에서 모니터링/상태 범주로 판단되는 기존 템플릿을 모두 Read했습니다: `SystemStatusBoard.tsx`, `MonitoringBoard.tsx`.

- `SystemStatusBoard`: 전체 상태 배너(overall.status/message) + 시스템별 상태 목록(`SystemStatusItem` — status enum `operational/degraded/outage/maintenance`, uptime, `UptimeHistoryStrip` 일별 이력) + 장애 이력(`IncidentRecord` — status enum `investigating/monitoring/resolved`, 타임스탬프 업데이트 목록) 구조로, Statuspage 벤치마크의 핵심 섹션(전체 상태 배너 · 컴포넌트별 상태 · 업타임 이력 · 인시던트 타임라인)과 **거의 100% 겹칩니다**. 실제로 기존 Storybook 스토리(`SystemStatus`, `Business.stories.tsx:391`)가 이미 ERP/OMS/WMS/PRM/그룹웨어/팀즈를 소재로 한 Statuspage류 화면을 재현해두었습니다.
- `MonitoringBoard`: 실시간 KPI 카드 + 설비(station) 가동 현황 + 차트를 다루는 제조/설비 모니터링 대시보드로, 상태 페이지(status page)가 아닌 운영 대시보드(operations dashboard) 패턴이라 BM08과 목적이 다릅니다(상태 히스토리·장애 공지 이력 없음).

**결론**: 정책 2-1항에 따라 `SystemStatusBoard`와 구조가 겹치므로 신규 템플릿 파일을 만들지 않습니다. 대신 벤치마크 대비 갭으로 판단된 두 가지 — (1) 컴포넌트 그룹핑(Statuspage의 "component groups"), (2) 과거 장애와 분리된 예정된 점검(Scheduled Maintenance) 섹션 — 을 기존 `SystemStatusBoard`의 prop 확장으로만 처리했습니다. `SystemStatusItem`에 선택적 `group?: string`을 추가해 미지정 시 기존 단일 목록과 동일하게 렌더링되도록 했고(하위 호환), 신규 `MaintenanceRecord[]`(`maintenances` prop, status enum `scheduled/in-progress/completed`)로 예정된 점검을 장애 이력과 분리된 섹션으로 추가했습니다. 새 파일은 없으며, `src/templates/index.ts`에는 신규 타입(`MaintenanceRecord`, `MaintenanceStatus`) export만 추가했습니다. Storybook에는 그룹핑·점검 섹션을 보여주는 스토리 `SystemStatusGrouped`(export명, story id `templates-business--system-status-grouped`)를 신규로 추가했습니다(정책 2-2항).

### 갭 목록

1. **[design-system-gap → 해소 완료]** 컴포넌트 그룹핑 부재: 기존 `SystemStatusBoard`는 `systems`를 평면 목록으로만 렌더링해 Statuspage의 "component groups"(예: API/웹사이트/DB군)에 해당하는 구조가 없었음. `SystemStatusItem.group?: string`과 `groupSystems()` 렌더 로직을 추가해 해소함(하위 호환: `group` 미지정 시 기존과 동일하게 단일 목록 렌더링).
2. **[design-system-gap → 해소 완료]** 예정된 점검(Scheduled Maintenance) 섹션 부재: 기존 `IncidentRecord.status`는 `investigating/monitoring/resolved`만 지원해 "예정된" 미래 점검을 과거 장애 이력과 동일 섹션에 섞어야 했음. `MaintenanceRecord`(`scheduled/in-progress/completed`) 타입과 `maintenances` prop, 별도 "예정된 점검" 섹션을 추가해 해소함.
3. **[execution-issue]** `UptimeHistoryStrip`의 일별 이력 블록이 이번 캡처(`docs/loop/screenshots/2026-09-21-ours.png`)에서 시각적으로 거의 식별되지 않음(전부 `operational`(초록) 상태라 배경과 대비가 약하거나 레이아웃 이슈일 가능성). 컴포넌트 코드(`src/components/data/UptimeHistoryStrip.tsx:56-63`)는 `h-6` 높이의 색상 블록과 `Tooltip`을 렌더링하도록 이미 구현되어 있어 컴포넌트 부재가 아니며, 이번 사이클 범위(그룹핑·예정 점검)와 무관한 기존 컴포넌트의 표시 이슈이므로 시스템 변경 없이 리포트에만 기록합니다. 필요 시 별도 사이클에서 `UptimeHistoryStrip` 단독 스토리로 재현·조사가 필요합니다.
