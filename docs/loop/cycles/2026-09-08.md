## 오늘의 스코프

`docs/loop/backlog.md`에서 status가 "대기"이면서 source가 `human-added` 또는 `eval-found`인 항목을 먼저 확인했습니다. 정책 7항에 따라 사람이 등록했거나 평가에서 발견된 갭 항목은 벤치마크 순회보다 우선 소비해야 하기 때문입니다. 검토 결과 B001~B015가 모두 "완료" 상태이며 "대기" 항목이 하나도 없어, benchmark-suite 고정 목록을 cursor 순서대로 소비합니다.

`docs/loop/benchmark-suite.md`의 frontmatter cursor 값은 1이고 표는 10개 행(BM01~BM10)이므로, 0-based 인덱스 1에 해당하는 **BM02 — GitHub Issues 리스트 (공개 저장소)**(https://github.com/facebook/react/issues, 패턴: 리스트/필터)를 오늘의 벤치마크로 선택합니다. 직전 사이클(2026-09-03)에서 BM01(cursor 0)을 소비하며 cursor를 1로 갱신했으므로 이번 사이클은 그 다음 항목을 이어서 처리합니다. 처리 후 cursor는 (1+1) % 10 = 2로 갱신했습니다.

BM02는 공개 저장소의 이슈 목록 화면으로, 상단 필터/검색 바 + 라벨·상태·담당자 등의 조건 필터 + 각 행에 제목·라벨·상태·메타(작성자/코멘트 수/업데이트 시각)를 담은 밀집 리스트로 구성된 "리스트/필터" 패턴에 해당합니다. 구조적으로는 기간계(business/admin)의 업무 리스트·필터 조회 화면(예: 주문·작업·요청 목록)과 재활용 축이 겹치므로, 재현·평가 시 다음 정책 가드레일을 유의합니다.

- 정책 3항(축 분리): 이 패턴이 기간계(business/admin)와 일반 웹사이트(service) 중 어느 축에 해당하는지 먼저 판단하고, 그 축 안에서 이미 있는 패턴과 겹치지 않는 갭만 채택합니다. BM02는 로그인 이후 업무성 목록 조회에 가까운 business 축이므로, 두 축을 뒤섞은 패턴은 채택하지 않습니다.
- 정책 2항(중복 금지, DRY): 신규 작업에 앞서 `src/components/`·`src/templates/`(특히 기존 ListSearchTable, Global Search Results(B007), Table/Tag/StatusBadge/Filter 관련 자산)를 대조해 리스트/필터 조회와 목적이 겹치는 자산이 이미 있는지 확인한 뒤에만 추가 범위를 확정합니다. 목적이 겹치는 기존 패턴이 있으면 반복 채택하지 않습니다.
- 정책 8항(갭 승격 기준): 발견된 부족 항목을 design-system-gap(구조적 부재)과 execution-issue(실행 품질 이슈)로 구분해, design-system-gap으로 판정된 경우에만 컴포넌트/토큰을 추가합니다. execution-issue는 시스템을 변경하지 않고 리포트에만 기록합니다.
- 정책 9항(일관성 유지): 업그레이드가 필요하더라도 전체 컨셉·스타일을 유지하는 범위 내 추가만 허용하며, 기존 시맨틱 토큰 체계 밖의 색상값 하드코딩이나 새로운 스타일링 체계 도입은 금지합니다.
- 정책 5항(병합 게이트): 모든 변경은 `develop` 대상 PR로만 제출하며, `main`/`develop` 직접 push는 금지합니다.

benchmark-suite 항목을 선택했으므로 `docs/loop/backlog.md`의 status는 이번 사이클에서 변경하지 않으며, benchmark-suite의 cursor만 1에서 2로 갱신했습니다.

## 완성도 평가

- 벤치마크: BM02 — GitHub Issues 리스트 (공개 저장소), https://github.com/facebook/react/issues
- 오늘 구현한 스토리: title `Templates/Business`, export `IssueList` (story id `templates-business--issue-list`, 내부 템플릿 컴포넌트 `IssueListBoard`)
- 스크린샷: 자사 `docs/loop/screenshots/2026-09-08-ours.png`
- **기술적 한계**: 이번 세션의 아웃바운드 프록시가 `github.com` 도메인 전체를 저장소 접근 게이트(git clone/API 전용) 뒤에 두고 있어, Playwright로 벤치마크 URL에 접속하면 실제 페이지 대신 `{"message":"GitHub access to this repository is not enabled..."}` / `{"message":"Request path could not be canonicalized."}` JSON 오류만 캡처됩니다. `add_repo`로 `facebook/react`의 읽기 접근(git clone 경로)은 확인했지만 이는 일반 웹 페이지 로드(HTTPS 프록시)에는 적용되지 않아, 이 세션에서는 벤치마크 페이지의 실제 스크린샷을 확보할 수 없었습니다. 따라서 벤치마크 스크린샷은 저장하지 않았고(`benchmarkScreenshotPath`는 빈 문자열로 보고), 아래 채점은 GitHub Issues 리스트 UI에 대한 사전 지식(레이아웃 구조·필터·라벨 색상·리스트 행 구성)에 기반한 것으로, 실제 이미지 대 이미지 비교보다 신뢰도가 낮다는 점을 명시합니다.
- 이번 갱신에서 `src/components/data/ColorTag.tsx`, `src/components/form/MultiSelect.tsx`, `src/components/overlay/Popover.tsx`·`Tooltip.tsx`, `src/components/foundation/Icon.tsx`를 직접 재확인해, 이전 버전 평가에 있던 "MultiSelect 부재" 기록이 사실과 달랐음을 정정했습니다(`MultiSelect`는 이미 존재하며 `IssueList` 스토리의 라벨 필터에 실제로 사용 중).

### 갭 목록

1. **이슈 라벨에 `ColorTag` 미사용(중립색 `Tag`만 사용)** — `execution-issue`
   - `IssueListBoard.tsx`는 `issue.labels`를 `Tag`(`src/components/data/Tag.tsx`, 항상 중립 회색)로만 렌더링합니다. 정확히 이 용도(부서/영역별 색상 구분)로 이미 존재하는 `ColorTag`(`src/components/data/ColorTag.tsx`, `brand`/`success`/`warning`/`danger`/`info` variant 지원)를 확인했으나 사용하지 않아, GitHub 특유의 라벨별 색상 구분이 재현되지 않았습니다. 컴포넌트가 이미 있으므로 실행 이슈로 분류합니다.
2. **이슈 상태(열림/닫힘) 전용 아이콘 부재** — `design-system-gap`
   - `src/components/foundation/Icon.tsx`를 확인한 결과 `IconName` 타입이 `'search' | 'comment'` 두 개뿐이며, GitHub Issues의 `issue-opened`/`issue-closed` 같은 상태 전용 아이콘이 시스템에 아예 없습니다. 이 때문에 `IssueListBoard`는 단순 색상 점(dot)으로만 상태를 표시합니다. 상응 아이콘/패턴이 `src/components`에 존재하지 않음을 확인했으므로 구조적 부재로 분류합니다.
3. **선택 항목 일괄 작업 툴바 미구현** — `execution-issue`
   - `IssueListBoard`는 `selectedIds.length > 0`일 때 "N개 선택됨" 텍스트만 노출하고 닫기/라벨 지정/담당자 지정 등 실행 버튼이 없습니다. `src/components/foundation/Button.tsx`가 이미 존재하므로 컴포넌트 부재가 아니라 이번 구현에서 활용하지 않은 실행 이슈입니다.
4. **담당자 아바타 호버 카드/프로필 미리보기 부재** — `execution-issue`
   - GitHub은 담당자 아바타에 마우스를 올리면 프로필 미리보기가 뜨지만, `IssueListBoard`의 `Avatar`는 정적 이니셜만 표시합니다. `src/components/overlay/Popover.tsx`, `Tooltip.tsx`가 이미 존재하므로 이번 구현에서 연결하지 않은 실행 이슈로 분류합니다.
