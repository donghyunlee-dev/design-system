# 디자인 토큰 스케일 재설계 + 블로그 템플릿 도입 설계

- 작성일: 2026-09-11
- 상태: 검토 대기 (구현 착수 전)
- 범위: 전역 타이포/레이아웃 토큰 축 신설 + 타입 스케일 재설계 + 블로그 템플릿 4종
- 변경 이력: 2026-09-11 밀도 모드(`data-density`) 설계 기각, 2층 구조로 단순화 (3절 참조)

---

## 1. 결론 요약

문제는 "블로그 토큰이 없다"가 아니라 **디자인 시스템에 타이포그래피 축 자체가 없다**는 것입니다.
따라서 블로그 전용 네임스페이스를 만드는 대신, **빠져 있는 전역 토큰 축을 신설하고 타입 스케일을 재설계**합니다.
블로그 템플릿 4종은 이 신규 토큰의 **검증 수단이자 첫 소비처**로 함께 구축합니다.

**최종 성공 기준:** `BlogCardGrid`로 벤치마크(`studeo.com.au/insights/`)를 재현하되, **Tailwind 임의값 0건 / 토큰 커버리지 90% 이상 / 블로그 전용 토큰 3개 이하**를 동시에 만족해야 합니다. (7-4 참조)

## 2. 현황 실측 (2026-09-11)

전체 토큰 **119개 중 색상이 90개**입니다.

| 축 | 토큰 | 컴포넌트 실제 사용 |
|---|---|---|
| 색상 | 90개 | 토큰 기반 (정상) |
| spacing | 16개 | 토큰 기반 (정상) |
| radius / shadow / motion | 13개 | 토큰 기반 (정상) |
| **font-size** | **0개** | `text-sm` 211, `text-xs` 158, `text-2xl` 54, `text-base` 15, `text-xl` 9, `text-lg` 8, `text-3xl` 6, `text-4xl` 4, `text-5xl` 2 |
| **font-weight** | **0개** | `font-semibold` 96, `font-medium` 81, `font-bold` 66, `font-normal` 4 |
| **line-height / letter-spacing** | **0개** | `leading-relaxed` 19, `tracking-wider` 18, `tracking-wide` 15, `tracking-tight` 5 … |
| **콘텐츠 폭** | **0개** | `max-w-7xl` 15, `max-w-6xl` 15, `max-w-xl` 11, `max-w-5xl` 11, `max-w-xs` 9 … |
| **z-index** | **0개** | `z-50` 7, `z-40` 1, `z-10` 1 |
| **border-width / opacity / aspect-ratio** | **0개** | 전부 하드코딩 |

**진단:** 현재 시스템은 "색상 시스템 + Tailwind 기본값"입니다. 브랜드 색을 교체해도 글자 위계·여백 리듬은 바뀌지 않으며, 화면마다 `max-w-*`가 제각각이라 레이아웃 일관성을 토큰으로 보장하지 못합니다.

### 2-1. 사실 정정

이전 초안에서 "`semantic.css`는 design-system 스킬이 자동 생성하므로 수정 위험"이라고 적었으나, `~/.claude/skills/design-system/` 전체를 확인한 결과 **`tokens/semantic.css`를 언급하는 내용이 없습니다.** 파일 상단 주석은 과거 워크플로의 흔적입니다. → 타이포 토큰을 `semantic.css`에 정상 배치합니다. `--blog-*` 격리 설계는 철회합니다.

## 3. 검토했으나 기각한 설계: 밀도 모드

초안에서는 기간계(고밀도)와 블로그(저밀도)의 요구가 상충하므로 `data-density="compact" | "editorial"` 런타임 모드로 역할 토큰을 통째로 재배정하는 3층 구조를 제안했습니다. **이 설계는 기각합니다.**

**기각 사유 1 — 이번 요구에 불필요합니다.**
밀도 모드가 필요한 조건은 "동일 컴포넌트가 두 밀도로 렌더링되어야 할 때"입니다. 그러나 블로그는 별도 템플릿 파일입니다. `BlogArticle`이 본문에 `--font-size-body-lg`(18px)를, `DataTablePage`가 `--font-size-body`(14px)를 참조하면 그것으로 해결됩니다. 역할 토큰 계층만으로 충분하며, 런타임 전환 축은 요구되지 않았습니다.

**기각 사유 2 — 모드가 늘어날 때 유지보수 비용이 곱셈으로 증가합니다.**
역할 11종 × 속성 4개 = **모드당 44개 토큰**입니다.

| 모드 수 | 타이포 토큰 수 |
|---|---|
| 1 (모드 없음) | 44개 |
| 2 (compact / editorial) | 88개 |
| 3 | 132개 |

3번째 모드 후보가 이미 저장소에 존재합니다 — `src/templates/business/DocumentPrint.tsx`. 인쇄 화면은 전형적인 별도 밀도 요구이며, 모바일까지 포함하면 4번째가 됩니다. 모드를 추가할 때마다 44개를 전부 재배정해야 하고, 누락된 토큰은 해당 화면에서만 조용히 깨집니다. 제어 축을 늘리는 대신 유지보수 부채를 곱셈으로 늘리는 구조입니다.

밀도 모드 자체는 업계에 선례가 있는 개념입니다(IBM Carbon의 productive / expressive 타입셋). 다만 그것은 다수 제품을 지탱하는 규모에서 정당화되는 선택이며, 현 시점의 이 저장소에서는 비용을 치를 근거가 없습니다.

**결론: 2층 구조를 채택합니다.**

```
[1층] 타입 래더 (base.css)       — 크기 사다리 하나 (11px ~ 72px, 11칸)
         ↓
[2층] 역할 토큰 (semantic.css)   — display / h1~h4 / body-lg / body / body-sm / caption / overline / code
                                    블로그는 여유로운 칸을, 기간계는 촘촘한 칸을 선택해 사용
```

## 4. 신설 토큰 설계

### 4-1. 타입 래더 (`tokens/base.css`)

rem 기반 모듈러 스케일(비율 1.2 기준, 반올림 보정):

| 토큰 | 값 | 비고 |
|---|---|---|
| `--text-2xs` | 0.6875rem (11px) | 신규 칸 (현재 `text-xs`보다 아래) |
| `--text-xs` | 0.75rem (12px) | |
| `--text-sm` | 0.875rem (14px) | |
| `--text-md` | 1rem (16px) | |
| `--text-lg` | 1.125rem (18px) | |
| `--text-xl` | 1.375rem (22px) | |
| `--text-2xl` | 1.75rem (28px) | |
| `--text-3xl` | 2.25rem (36px) | |
| `--text-4xl` | 3rem (48px) | |
| `--text-5xl` | 3.75rem (60px) | |
| `--text-6xl` | 4.5rem (72px) | 신규 칸 (매거진 헤드라인용) |

함께 신설 (**칸 수는 실사용 실측 기준**으로 확정):

| 축 | 칸 | 근거 |
|---|---|---|
| `--weight-normal/medium/semibold/bold` | 4 | 실사용 4종 전부 (`semibold` 96, `medium` 81, `bold` 66, `normal` 4) |
| `--leading-none/tight/normal/relaxed` | 4 | 실사용 3종(`relaxed` 19, `none` 4, `tight` 3) + 본문 기본값 `normal`. `snug`·`loose`는 사용처가 없어 제외 |
| `--tracking-tight/normal/wide/wider/widest` | 5 | 실사용 4종(`wider` 18, `wide` 15, `tight` 5, `widest` 3) + 리셋용 `normal`. `tighter`는 사용처가 없어 제외 |

### 4-2. 역할 토큰 (`tokens/semantic.css`)

역할 11종: `display`, `h1`, `h2`, `h3`, `h4`, `body-lg`, `body`, `body-sm`, `caption`, `overline`, `code`

**모든 역할에 4속성을 전부 부여하지 않습니다.** 실사용상 `tracking`은 대부분 `normal`이고 `weight`도 본문 계열은 유틸리티 클래스로 충분합니다. 필요한 곳에만 부여합니다.

| 속성 | 부여 대상 | 개수 |
|---|---|---|
| `--font-size-*` | 역할 11종 전부 | 11 |
| `--font-leading-*` | 역할 11종 전부 | 11 |
| `--font-weight-*` | `display`, `h1`~`h4`, `overline` | 6 |
| `--font-tracking-*` | `display`, `h1`, `overline` | 3 |

**합계 31개.** (전 역할 × 4속성이면 44개였습니다.)

### 4-3. 나머지 신설 축

**채택**

| 축 | 토큰 | 개수 | 대체 대상 |
|---|---|---|---|
| 콘텐츠 폭 | `--measure-prose`(68ch), `--measure-narrow`(52ch) | 2 | 본문 가독 폭 (신규) |
| 레이아웃 폭 | `--width-content-sm/md/lg/xl` | 4 | 하드코딩 `max-w-*` 74곳 |
| 종횡비 | `--aspect-wide`(16/9), `--aspect-card`(3/2), `--aspect-square` | 3 | 썸네일 (신규) |

**기각** — 아래 3개 축은 초안에 있었으나 실사용 근거가 부족하고 7-4 벤치마크로 검증되지도 않아 제외합니다. 검증 수단이 없는 토큰은 사용되지 않은 채 남습니다.

| 축 | 기각 사유 |
|---|---|
| z-index (8개) | 코드 전체 사용처가 9곳(`z-50` 7, `z-40` 1, `z-10` 1). 9곳을 위해 8개 토큰을 두는 것은 과합니다. 블로그와 무관 |
| border-width (3개) | 실사용은 `border-b-2` 7곳, `border-2` 4곳. Tailwind 기본 유틸리티로 충분 |
| opacity (3개) | 실사용이 `opacity-50/60/40/90/80/0/100`, `bg-black/50`, `bg-black/40`으로 산포. 시맨틱 3개로 덮이지 않으며, 덮은 것처럼 보이게만 만듭니다 |

세 축 모두 필요성이 실증되면 후속 과제로 별도 처리합니다.

### 4-3-1. 신규 토큰 총계

**64개** (현재 119 → **약 183개**)

| 구분 | 개수 |
|---|---|
| 타입 래더 | 11 |
| weight / leading / tracking | 13 |
| 역할 토큰 | 31 |
| measure / width-content / aspect | 9 |
| **합계** | **64** |

블로그 전용(`--blog-*`)은 **0개**를 목표로 하며, 정말 블로그에서만 쓰이는 값이 남으면 그때만 추가합니다 (상한 3개, 7-4 V4).

> **수치 정정:** 초안에서 밀도 모드 기각 후 신규 토큰을 "약 46개"로 기재했으나 오산이었습니다. 당시 설계의 실제 합계는 97개였고, 위 YAGNI 축소(z-index·border-width·opacity 축 기각, leading·tracking·aspect 칸 축소, 역할 토큰 속성 선별)를 거쳐 64개로 확정했습니다.

### 4-4. Tailwind 연결

`tailwind.config.js`의 `fontSize`에 두 계열을 모두 등록합니다.

1. **역할 키 신설**: `text-display`, `text-h1`~`text-h4`, `text-body`, `text-caption`, `text-overline` 등 → 신규 템플릿이 사용
2. **기존 키 재매핑**: `xs`/`sm`/`base`/`lg`/`xl`/`2xl`… 을 새 래더 변수로 연결

2번이 핵심입니다. **기존 컴포넌트 400여 곳의 클래스명을 한 줄도 고치지 않고도 새 스케일이 전면 적용됩니다.** 재설계 요구를 충족하면서 대규모 수정의 위험을 제거합니다.

단, 일부 칸의 실제 픽셀 값이 Tailwind 기본값과 달라집니다(예: `text-xl` 20px → 22px, `text-2xl` 24px → 28px). **이는 의도된 변화이며, 5절의 회귀 검증으로 결과를 확인합니다.**

## 5. 회귀 검증 수단 (Chromatic 대체)

Chromatic은 현재 저장소에 없습니다(`.github/workflows/`에 `deploy-storybook.yml`, `publish-npm.yml` 2개뿐). 타입 스케일 재설계는 **모든 화면에 영향을 주므로 검증 없이는 진행할 수 없습니다.**

**로컬 스크린샷 회귀 하네스를 먼저 구축합니다.**

- `playwright`를 devDependency로 추가 (신규 의존성 1개)
- `scripts/visual-snapshot.mjs`: `storybook-static`을 띄우고 `index.json`의 전 스토리(**236개**)를 순회하며 PNG 캡처
- `npm run snapshot:base` → 변경 전 기준선, `npm run snapshot:diff` → 변경 후 비교 및 변경 목록 출력
- 산출물은 `.gitignore` 처리 (저장소에 PNG 미커밋)

이 하네스는 이번 작업 이후에도 계속 자산으로 남습니다.

## 6. 블로그 템플릿 (4종)

`src/templates/service/blog/` — 본문·제목에 역할 토큰의 여유로운 칸(`body-lg`, `display` 등)을 선택해 사용

| 템플릿 | 성격 | 검증하는 토큰 |
|---|---|---|
| `BlogCardGrid` | 카드 3열 그리드 + 카테고리 필터 | `--aspect-*`, `--width-content-*`, 카드 타이포 위계 |
| `BlogMagazine` | 대형 피처드 글 + 하위 리스트 | `--text-5xl/6xl`, `--tracking-tighter`, `--leading-none` |
| `BlogMinimalList` | 썸네일 없는 텍스트 리스트 | `--font-size-overline`, `--font-tracking-overline`, 여백 리듬 |
| `BlogArticle` | 글 상세 (본문 + 목차 + 관련 글) | `--measure-prose`, `--font-leading-body`, `--font-size-body-lg` |

각 템플릿은 다크모드를 전역 토큰으로 상속하므로 별도 대응이 없습니다.
참고 사이트는 **레이아웃 패턴만** 가져오고 색·크기 값은 그대로 쓰지 않습니다. 매거진형과 미니멀형은 별개 템플릿으로 분리해 한 화면 안에서 톤이 섞이지 않게 합니다.

### 7-4. 검증 단계 (최종 성공 기준)

**목표: 사내 블로그를 벤치마크 수준의 디자인으로, 신규 토큰만 써서 구현할 수 있다.**

`BlogCardGrid`를 `studeo.com.au/insights/`의 재현 대상으로 두고 다음 4개를 모두 통과해야 합니다.

| # | 성공 기준 | 측정 방법 | 합격선 |
|---|---|---|---|
| V1 | **임의값 0건** — 블로그 템플릿이 토큰 밖의 값을 쓰지 않음 | `src/templates/service/blog/` 대상으로 Tailwind 임의값 문법(`text-[`, `w-[`, `gap-[`, `max-w-[`, `leading-[`, `p-[`)과 인라인 `px` 하드코딩을 grep | **0건** |
| V2 | **토큰 커버리지** — 재현에 필요한 값 중 토큰으로 표현된 비율 | P1 계측 항목 대비 토큰으로 충족한 항목 수 | **90% 이상** |
| V3 | **구조 재현** — 벤치마크의 레이아웃 구조가 재현됨 | 카드 그리드 3열→2열→1열, 카테고리 필터, 썸네일 종횡비, 카드 내부 요소 위계(태그/제목/날짜)를 항목별 대조 | **전 항목 충족** |
| V4 | **시스템 오염 0건** — 블로그 구현이 전역을 더럽히지 않음 | 블로그 전용 토큰(`--blog-*`) 개수 | **3개 이하** (0개 목표) |

**V2에서 미달한 항목의 처리 원칙** (growth-loop 방식): 부족분을 블로그에만 급히 때워 넣지 않습니다. 각 미달 항목을 아래 둘 중 하나로 판정해 기록합니다.

- **구조적 결함** → 전역 래더/역할 토큰에 정식 승격 (시스템 업그레이드)
- **벤치마크 고유 표현** → 채택하지 않고 기각 사유를 기록 (시스템 미변경)

이 판정 기록은 P1 계측 결과와 같은 파일(`docs/benchmarks/studeo-insights.md`)에 이어 붙여, 다음 벤치마크 작업 때 중복 검토를 피합니다.

**최종 산출물 확인:** V1~V4 통과 + 7-3 전 항목 통과 시 "사내 블로그를 신규 토큰으로 디자인 가능"이 입증된 것으로 봅니다.
