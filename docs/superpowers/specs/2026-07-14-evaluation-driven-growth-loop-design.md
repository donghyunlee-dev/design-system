# 평가 주도 성장 루프 (Evaluation-Driven Growth Loop) 설계

## 배경 및 문제의식

기존 `growth-loop-daily-cycle.js`는 "매일 새 업무 템플릿 1개를 추가"하는 생산 루프였다. 벤치마크 비교 단계가 있었지만 결과는 "참고용 소견"에 그쳤고, 디자인 시스템 자체의 개선으로 이어지지 않았다. 또한 정책에 "로그인 없는 유명 IT 사이트를 벤치마크로 삼으라"는 지시가 있었지만, PM 에이전트가 매 사이클 즉흥적으로 벤치마크를 골랐기 때문에 실제로는 마케팅 랜딩 페이지 위주로 얕게 소비되었고, 백로그가 소진되면 즉흥적으로 새 템플릿을 제안해야 하는 구조라 갈수록 억지스러운 항목이 나올 위험이 있었다.

디자인 시스템의 존재 이유는 "웹사이트 화면 설계를 맡겼을 때 구조와 완성도 높은 사이트를 만들어낼 수 있는가"이다. 이를 검증하는 가장 직접적인 방법은 실제 유명 사이트의 페이지를 디자인 시스템만으로 재현해보고, 얼마나 근접했는지 채점하고, 부족한 지점(컴포넌트/토큰/패턴의 부재)을 디자인 시스템 자체의 업그레이드로 되먹임하는 것이다. 이 문서는 그 방향으로 `growth-loop-daily-cycle.js`를 전면 개편하는 설계를 정의한다.

## 전체 흐름

기존 일일 루틴을 완전히 대체한다 (병행 루틴 없음).

```
1. Select    — 오늘 재현할 벤치마크 페이지 1개 선정
2. Reproduce — 디자인 시스템 컴포넌트/토큰만으로 그 페이지를 최대한 재현 (신규 템플릿으로 구현)
3. QA        — build / test / build-storybook (기존과 동일)
4. Evaluate  — LLM 심사자가 벤치마크 스크린샷 vs 재현 스크린샷을 항목별 1~5점 채점 + 구조적 갭 목록 반환
5. Upgrade?  — 갭이 "디자인 시스템 자체의 부재"로 판정되면, 그 자리에서 컴포넌트/토큰을 보강하고 페이지를 다시 구현
6. Consistency Check — 업그레이드가 기존 토큰/컴포지션 방식을 위반하지 않았는지 검증. 위반 시 해당 변경만 되돌리고 기존 컴포넌트로 근사
7. Re-evaluate — 최대 1회만 재평가 (무한루프 방지). 그래도 부족하면 결과를 있는 그대로 기록하고 종료
8. PR        — 재현 페이지 + (있다면) 디자인 시스템 업그레이드 + 평가 리포트를 하나의 PR로 제출
```

재현 페이지는 일회성 산출물이 아니라 기존과 동일하게 `src/templates/`에 실제 템플릿으로 남고 Storybook 스토리도 추가된다 — 평가용 부산물이 아니라 그 자체로 프로덕션 가치를 갖는다.

## Select 단계 — 벤치마크 선정 우선순위

1. `docs/loop/backlog.md`에 사람이 등록한 `human-added` 항목(status: 대기)이 있으면 최우선으로 그 항목을 처리한다 (기존 정책 유지).
2. 없으면 `docs/loop/benchmark-suite.md`의 고정 목록에서 `cursor` 인덱스가 가리키는 다음 페이지를 선택한다.
3. 사이클 종료 시 `cursor`를 `+1`하고, 목록 끝에 도달하면 `0`으로 되돌려 처음부터 다시 순회한다(회귀 테스트 성격 — 디자인 시스템이 바뀐 뒤 같은 페이지를 다시 재현하면 점수가 실제로 올랐는지 확인 가능).

## 벤치마크 목록 관리 — `docs/loop/benchmark-suite.md` (신규)

사람이 직접 관리하는 고정 목록. PM 에이전트는 이 파일을 **읽기만** 하며 수정하지 않는다(권한상 `docs/loop/policy.md`와 동급).

```markdown
---
type: benchmark-suite
last_updated: 2026-07-14
cursor: 0
---

| id | site | page | url | pattern | added_on |
|---|---|---|---|---|---|
| BM01 | Linear | 홈페이지 | https://linear.app | 랜딩/마케팅 | 2026-07-14 |
| BM02 | Stripe | Docs 홈 | https://docs.stripe.com | 문서/네비게이션 | 2026-07-14 |
| BM03 | GitHub | 검색 결과 | https://github.com/search?q=react | 검색/리스트 | 2026-07-14 |
```

- 등록 시점에 로그인 없이 공개 접근 가능한 URL인지 사람이 직접 확인한다(기존 policy 7항 위반 가능성이 구조적으로 사라짐).
- 목록이 소진되면 루틴이 멈추지 않고 처음부터 다시 순회한다. 사람이 원하면 언제든 새 행을 추가해 목록을 확장할 수 있다.

## Evaluate 단계 — 채점 기준

LLM 심사자에게 벤치마크 스크린샷과 재현 스크린샷을 함께 제공하고 아래 5개 항목을 1~5점으로 채점하게 한다.

| 항목 | 확인 내용 |
|---|---|
| 레이아웃/구조 | 섹션 배치, 그리드, 정보 위계가 벤치마크와 얼마나 일치하는가 |
| 컴포넌트 충실도 | 벤치마크의 UI 요소(카드, 내비, 배지 등)를 상응하는 컴포넌트로 빠짐없이 표현했는가 |
| 타이포그래피/여백 | 폰트 크기 위계, 여백 리듬이 유사한가 |
| 인터랙션/상태 | hover, 빈 상태, 반응형 등 벤치마크에 있는 상태를 재현했는가 |
| 브랜드 톤 일관성 | @sfood/ui 톤을 유지하면서도 벤치마크의 완성도 수준에 도달했는가 |

### 갭 판정 로직 (핵심)

낮은 점수가 나온 항목마다 심사자는 원인을 다음 둘 중 하나로 분류해야 한다:

- **① 구조적 부재 (`design-system-gap`)**: 상응하는 컴포넌트/토큰/패턴이 디자인 시스템에 아예 없어서 표현하지 못함 → Upgrade 단계로 승격.
- **② 실행 품질 이슈**: 컴포넌트/토큰은 있는데 구현 에이전트가 제대로 활용하지 못함(예: 존재하는 spacing 토큰을 안 썼음) → 시스템은 변경하지 않고 리포트에만 기록.

"도구가 없어서 못한 것"과 "도구는 있는데 실력이 부족했던 것"을 분리해야 디자인 시스템이 불필요하게 비대해지는 것을 막을 수 있다.

## Upgrade 단계

`design-system-gap`으로 승격된 항목에 대해서만 컴포넌트/토큰을 보강하고 같은 사이클 안에서 페이지를 다시 구현한 뒤 재평가한다. 재평가는 **최대 1회**로 제한한다 — 그래도 부족하면 결과를 있는 그대로 PR에 기록하고 사이클을 종료한다(무한 재시도 방지, 사이클 소요 시간 예측 가능성 확보).

### Consistency Check — 디자인 시스템 일관성 가드레일

전체 디자인 시스템의 컨셉과 스타일이 흔들리는 판단/업그레이드가 발생해서는 안 된다. Upgrade 단계 직후, 재평가 이전에 별도 검증 에이전트가 diff를 감사한다.

**검증 항목**:
- 신규 컴포넌트/스타일이 기존 토큰(색상/spacing/typography/shadow 스케일) 이외의 값을 하드코딩했는가
- 기존 컴포지션 방식(`cn` 유틸, variant prop 패턴, Card/Stack 등 primitives 조합)과 다른 스타일링 기법(인라인 style, 별도 CSS 파일, 새 스타일링 라이브러리 등)을 도입했는가
- 기존 컴포넌트 파일을 "추가"가 아니라 "변경"해서 기존 화면들의 시각적 결과를 건드렸는가

**위반 시 대응**: 위반된 신규 컴포넌트/토큰 변경만 되돌리고, 페이지는 가장 가까운 기존 컴포넌트로 대체·근사해 재구현한 뒤 그대로 PR을 제출한다. 이 갭은 "미해결 상태"로 남기고, cycle log에 "일관성 위반으로 시스템 변경 보류 — 사람 판단 필요"라고 기록한 뒤 `docs/loop/backlog.md`에 `human-added`급 검토 항목으로 등록한다. 사이클은 절대 산출물 없이 끝나지 않는다 — 페이지 구현 자체는 항상 PR로 나간다.

## 문서 스키마 변경

### `docs/loop/backlog.md` — 역할 변경

기존에는 "새로 만들 템플릿 후보" 목록이었으나, 이제 **디자인 시스템 갭 백로그**로 의미가 바뀐다.

- `source` 컬럼 값은 `human-added`(사람이 직접 요청) 또는 `eval-found`(평가에서 발견된 구조적 갭) 두 가지만 사용한다.
- 기존 `pm-proposed`(에이전트가 즉흥적으로 새 템플릿을 제안하는 경로)는 **폐지**한다. 이것이 정책 미준수의 근본 원인이었으므로, 새 백로그 항목이 생기는 경로를 사람 등록과 평가발견 두 가지로만 한정한다.

### `docs/loop/cycles/{date}.md` — 신규 섹션

```markdown
## 완성도 평가
- 벤치마크: BM03 GitHub 검색 결과 (https://github.com/search?q=react)
- 점수: 레이아웃 4 / 컴포넌트 충실도 3 / 타이포그래피 4 / 인터랙션 2 / 브랜드 톤 5
- 발견된 갭 (design-system-gap 승격): "패싯 필터 사이드바 컴포넌트 없음"
- 실행 단계 이슈 (승격 안 됨): "카드 간 여백이 벤치마크보다 좁음 — 기존 spacing 토큰으로 조정 가능했으나 누락"
- 보완 시도: FacetFilter 컴포넌트 신규 추가 → 재평가 결과: 컴포넌트 충실도 3→4
```

Plan(이제 Select) 단계에서 scopeItems가 비는 경우(사람 등록 항목도 없고 benchmark-suite.md도 비어있는 극단적 경우)는 이전 대화에서 지적한 "무기록 스킵" 문제를 함께 고쳐, 반드시 `status: skipped-empty-scope`로 cycle log를 남긴다.

### `docs/loop/policy.md` — 개정

- 7항(벤치마크 접근성) 문구를 "PM이 매번 고른다" → "benchmark-suite.md의 고정 목록에서 cursor 순서대로 소비한다"로 수정.
- 8항 신설: "갭은 design-system-gap으로 판정된 경우에만 시스템을 변경한다. 실행 품질 이슈는 시스템을 바꾸지 않는다."
- 9항 신설: "디자인 시스템 업그레이드는 전체 컨셉과 스타일을 유지하는 범위 내 추가만 허용한다. 기존 토큰/컴포지션 방식과 다른 스타일링 체계를 도입하거나 기존 컴포넌트의 시각적 결과를 바꾸는 변경은 금지하며, Consistency Check에서 자동 검출·롤백한다."
- 6항(일일 스코프 상한 1~3개) → 사이클당 재현 페이지 1개로 고정되므로 "1개"로 수정.

## 범위 밖 (이번 설계에 포함하지 않음)

- 여러 페이지로 구성된 사이트 전체 재현 (단일 페이지로 확정)
- 자동 정량 측정(픽셀 diff, DOM 구조 비교 등) — LLM 심사자 채점으로 대체
- 별도 평가 전용 스케줄(주 2회 등) — 기존 일일 루틴을 완전 대체하므로 불필요
