# 디자인 시스템 자동 성장 루프 — 정책/문서 체계 설계 (Phase 1)

## 배경 및 목적

`@sfood/ui`를 지속적으로 성장시키기 위해, 마스터 PM(Project Manager) 에이전트와 하위 에이전트(소스 수집, 컴포넌트 개발, 템플릿 개발, QA, 품질 비교)가 매일 1회 루틴으로 실행되며 결과를 PR로 쌓는 "루프 엔지니어링" 체계를 구축한다.

이 체계가 성립하려면 에이전트들이 실행마다 공유하는 "상태"가 문서로 존재해야 한다. 이 문서를 매번 사람이 새로 브리핑하지 않고, 에이전트가 스스로 읽고 써서 다음 실행에 이어가야 한다.

**범위**: 이 설계는 전체 루프 시스템 중 **문서/정책 체계**(1번 서브프로젝트)만 다룬다. 마스터 PM의 실제 판단 로직, 하위 에이전트 오케스트레이션(Workflow 스크립트), cron 스케줄링, PR 생성·스크린샷 캡처 자동화는 이 문서에서 정의한 스키마를 입출력으로 사용하는 **별도 후속 설계(Phase 2: 루틴 오케스트레이션)**에서 다룬다. 이번 설계에서는 실제 에이전트 프롬프트나 실행 스크립트를 작성하지 않는다.

## 설계 결정 요약

브레인스토밍 과정에서 확정된 정책 결정:

| 결정 사항 | 선택 |
|---|---|
| 방향성 설정 주체 | PM이 자율적으로 방향을 제안하되, 백로그에 등록해 근거를 남긴다 (즉흥 실행 금지) |
| 넘을 수 없는 가드레일 | 사람이 `policy.md`에 고정 — PM은 읽기 전용, 수정 불가 |
| 문서 형식 | YAML frontmatter + 마크다운 본문 (에이전트 파싱 안정성 우선) |
| 백로그 항목 출처 | PM 제안 + 사람 수동 추가 병용, 사람 추가 항목이 우선권을 가짐 |
| 사이클 기록 방식 | 날짜별 파일 분리 (`cycles/YYYY-MM-DD.md`) — PM이 매번 전체 이력을 다시 읽지 않아도 됨 |
| 품질 비교 벤치마크 사이트 | PM이 매 사이클 자율 선정, 사이클 로그에 사이트명·근거 기록 |
| 병합 정책 | 모든 변경은 PR로만, 사람이 다음날 확인 후 병합 (PR은 계속 쌓여도 무방) |

## 디렉터리 구조

```
docs/loop/
├── policy.md              # 고정 가드레일 (사람 소유, PM 수정 불가)
├── backlog.md             # 작업 후보 목록 (PM + 사람 병용)
└── cycles/
    ├── 2026-07-10.md       # 사이클별 실행 로그 (날짜별 파일)
    └── ...
```

기존 `docs/superpowers/`(브레인스토밍 스펙/플랜 — 한 번 쓰고 끝나는 설계 스냅샷)와는 성격이 달라 별도 디렉터리(`docs/loop/`)로 분리한다. `docs/loop/` 하위 문서는 에이전트가 매일 갱신하는 살아있는 상태다.

## `policy.md` 스키마

```yaml
---
type: policy
owner: human
mutable_by_pm: false
last_updated: YYYY-MM-DD
---
```

**초기 가드레일 (본문, 사람이 직접 정의·수정)**:

1. **라이선스**: MIT/Apache/BSD 등 permissive 라이선스의 디자인 시스템만 참고 대상으로 삼는다. 코드를 그대로 복사하지 않고, 레이아웃/구조만 참고해 `@sfood/ui` 기존 컴포넌트로 재구현한다.
2. **중복 금지 (DRY)**: 기존 `src/components/`, `src/templates/`와 목적이 겹치는 패턴은 채택하지 않는다. 채택 전 반드시 기존 컴포넌트/템플릿 목록과 대조한다.
3. **적합성**: 소비자용 마케팅/랜딩 트렌드보다 내부 업무 시스템에 적용 가능한 패턴(목록, 폼, 대시보드, 승인, 설정 등)을 우선한다.
4. **의존성 제한**: 신규 npm 패키지를 추가하지 않는다. 기존 디자인 토큰과 컴포넌트만으로 구현한다.
5. **병합 게이트**: 모든 변경은 PR로만 제출한다. `main` 직접 push 금지, 사람 승인 없이 병합 금지.
6. **일일 스코프 상한**: 하루 사이클당 백로그 1~3개 항목만 진행한다.

PM은 매 사이클 시작 시 이 문서를 읽기만 한다. 정책을 바꾸려면 사람이 `policy.md`를 직접 수정해야 한다.

## `backlog.md` 스키마

```yaml
---
type: backlog
last_updated: YYYY-MM-DD
---
```

항목 필드:

| 필드 | 설명 |
|---|---|
| `id` | 순번 (예: `B012`) |
| `title` | 후보명 |
| `source` | `pm-proposed` \| `human-added` |
| `status` | `대기` → `진행중` → `완료` \| `보류`(정책 위반 등으로 반려) |
| `rationale` | 필요 이유 1~2줄 |
| `added_on` | 추가 날짜 |
| `resolved_cycle` | 완료 시 처리된 사이클 로그 경로 (예: `cycles/2026-07-12.md`) |

규칙:
- PM은 매 사이클 시작 시 `대기` 상태 항목 중 사람이 추가한 항목을 우선으로, 그다음 PM 제안 항목 순으로 그날 스코프(1~3개, `policy.md` 6번 조항 상한 내)를 정한다.
- PM은 새 방향을 즉흥적으로 진행하지 않고, 반드시 `pm-proposed` 항목으로 백로그에 먼저 등록한 뒤(같은 사이클 내에서도 가능) 진행한다.
- 사람이 추가한 항목은 PM이 임의로 반려하거나 순서를 미룰 수 없다. `policy.md` 위반이 명백한 경우에만 `보류` 처리하고 사유를 `rationale`에 남긴다.

## `cycles/YYYY-MM-DD.md` 스키마

```yaml
---
type: cycle-log
date: YYYY-MM-DD
backlog_items: [B012, B013]
pr_url: null   # PR 생성 후 채움
status: in-progress   # in-progress | pr-open | merged | closed
---
```

**상태 전환 규칙**: PM이 브랜치와 cycle log를 만든 시점의 초기 상태는 `in-progress`이며, PR 생성 시 `pr-open`으로 갱신한다.

본문 구성:

1. **오늘의 스코프**: 진행한 백로그 항목 id와 선정 이유
2. **PM 방향 제안 로그** (해당 시): 새로 제안한 방향의 갭 분석 근거 + 등록한 `pm-proposed` 항목 id
3. **소스 수집 결과**: 검토한 외부 디자인 시스템/패턴, `policy.md` 가드레일 기준 채택/반려 여부와 사유
4. **구현 결과**: 생성/수정된 컴포넌트·템플릿 파일 목록
5. **QA 결과**: 타입체크·빌드·Storybook 빌드·접근성 검사 등 정량 지표 통과 여부
6. **품질 비교**: 벤치마크 사이트명·URL, 재현한 페이지, 스크린샷 경로(`docs/loop/screenshots/YYYY-MM-DD.png`), 비교 소견(참고용)
7. **PR 링크**: frontmatter `pr_url`과 동일하게 본문에도 명시

스크린샷은 `docs/loop/screenshots/YYYY-MM-DD.png`로 리포지토리에 커밋하고, PR 본문에도 동일 이미지를 첨부한다.

## 비목표 (Non-goals, 이번 설계 범위 밖)

- 마스터 PM/하위 에이전트의 실제 프롬프트, 모델 지정, Workflow 오케스트레이션 스크립트
- cron 트리거 설정 (`CronCreate` 등)
- PR 생성 자동화, 스크린샷 캡처 자동화(Playwright 등)의 구현 방법
- 위 항목들은 Phase 2(루틴 오케스트레이션) 설계에서 다룬다.

## 검증 방법

- `docs/loop/policy.md`, `backlog.md`를 실제로 생성하고, 백로그에 항목 1~2개를 수동으로 채워 스키마가 실제로 읽고 쓰기 편한지 확인한다.
- 사이클 로그 1개를 예시로 채워봐서(가상의 사이클) 7개 본문 섹션이 실제 정보로 자연스럽게 채워지는지 확인한다.
- 위 검증은 Phase 1 구현 계획(다음 단계, writing-plans)에서 실제 작업 항목으로 다룬다.
