# WindSoft Admin Design System Design

**상태:** 사용자 승인 — 2026-10-27

## 의도

참고용 UI 모음에서 실제 업무 프로젝트가 기본 컴포넌트와 템플릿을 골라 빠르게 완성할 수 있는 WindSoft 고유 디자인 시스템으로 발전시킨다. 목표 사용자는 React 기반 내부 관리 화면을 만드는 개발자와 그 화면을 매일 사용하는 운영 담당자다.

## 브랜드 근거

WindSoft 랜딩 페이지의 브랜드 섹션과 CSS에서 확인한 정보를 정체성의 출처로 삼는다.

- 메시지: “사람과 함께 흐르는 기술” / “Technology that flows with people.”
- 지향점: 유연성, 확장성, 실행력
- 색: Deep Navy `#0B2D5B`, Sky Blue `#3B82F6`, Cyan `#14B8A6`, Light Blue `#E0F2FF`, Soft Gray `#94A3B8`
- 서체: Pretendard Variable
- 사이트의 버튼과 카드 모서리는 약 5–9px 범위다. 관리 화면은 장식적 여백과 프로모션 레이아웃을 복사하지 않고 이 브랜드 성격만 계승한다.

참고 링크:

- [WindSoft 랜딩 및 브랜드 자료](https://windsoft.leedh84.chatgpt.site/)
- [IBM Carbon Data Table 규격](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/specifications)
- [GitHub Primer Typography 규칙](https://primer.style/product/getting-started/foundations/typography/)

Carbon은 데이터 밀도와 선택적 테이블 기능의 참고 대상으로, Primer는 rem 기반 타이포그래피·4px rhythm·읽기 위계의 참고 대상으로 쓴다. 어느 쪽의 시각 언어나 코드를 그대로 복사하지 않는다.

## 목표

- 토큰을 바꾸면 색, 글자 위계, 여백, 컨트롤 크기와 밀도가 기본 컴포넌트 및 템플릿에 일관되게 반영된다.
- 업무 화면의 가독성과 정보 밀도를 함께 확보한다.
- 입력, 탐색, 테이블, 피드백과 템플릿에서 상태·크기·접근성 규칙이 예측 가능하다.
- Storybook의 기본 미리보기는 WindSoft의 단일 기준 스타일을 사용하고, 지원 테마와 상태는 같은 스타일 규칙 안에서 비교할 수 있다.
- 개발자가 기본 컴포넌트 조합과 목적별 템플릿을 쉽게 찾아 재사용한다.

## 비목표

- WindSoft 마케팅 랜딩의 히어로, 스크롤 모션, 대형 전시 이미지와 넓은 섹션 여백을 관리 화면에 이식하지 않는다.
- 이번 작업에서 새 기능 컴포넌트를 많이 추가하거나 기존 API를 일괄 파기하지 않는다.
- Carbon, Primer 또는 다른 회사 디자인 시스템의 모양을 그대로 복제하지 않는다.
- 새로운 런타임·스타일링 의존성을 추가하지 않는다.

## 접근 방식

1. **랜딩 디자인을 그대로 관리 UI로 확장:** 브랜드 연속성은 높지만 홍보 페이지의 크기·여백·장식이 업무 흐름을 방해할 수 있어 제외한다.
2. **WindSoft 정체성 + 관리 UI 규칙:** 브랜드 팔레트, 서체와 성격은 유지하고, 정보 밀도·상태·접근성·데이터 표시 규칙은 Carbon/Primer를 참고해 새로 정한다. 목표와 기존 토큰 구조에 가장 잘 맞는 권고안이다.
3. **중립적인 관리 UI를 먼저 만들고 브랜드를 나중에 적용:** 중립 기준은 빠르게 잡을 수 있지만 브랜드 기준이 두 번 만들어지고 현재 WindSoft 정체성이 약해져 제외한다.

## 제안하는 시각·사용 규칙

아래 값은 시작점 제안이다. Foundation Storybook에서 실제 화면으로 확인한 뒤 확정한다.

- **톤:** 차분하고 명료하며 유연한 업무 도구. 네이비는 주요 동작의 기본 배경, 스카이블루는 포커스·링크·보조 강조, 시안은 제한적인 보조 accent로 사용한다. 전경색 조합은 대비를 측정해 정한다.
- **표면:** 기본 배경은 현재의 옅은 블루그레이 계열, 카드와 입력 표면은 흰색, 구분은 얇은 경계선을 우선한다. 그림자는 팝오버·모달 등 실제 부유 요소에 제한한다.
- **색 접근성:** `#94A3B8`은 브랜드 보조색으로 보존하되 작은 본문 텍스트에 무조건 사용하지 않는다. 본문 보조색은 현재의 더 진한 `#52677F` 등 대비를 만족하는 의미 토큰을 기준으로 한다. 모든 상태는 색상만으로 전달하지 않는다.
- **색 출처 정리:** 랜딩의 공식 색상 목록에는 `#3B82F6`이 Sky Blue로 나오지만 CSS에는 별도 `text-blue #2265D1`도 있다. 두 파랑의 역할과 대비를 조사해 공식 팔레트와 기능 토큰의 연결을 명확히 한다.
- **서체:** Pretendard Variable을 기본으로 유지하고 페이지 제목, 섹션 제목, 본문, 조밀한 데이터, 라벨, 보조 문구의 크기·굵기·행간을 역할 토큰으로 정한다. 값은 rem을 우선해 확대 설정을 존중한다.
- **간격:** 4px rhythm을 기준으로 `4, 8, 12, 16, 24, 32, 40, 48px` 후보를 사용한다. `max-w-sm/md/lg`와 충돌하지 않도록 Tailwind의 전역 spacing 키를 덮지 않고 이름 있는 CSS 변수로 제공한다.
- **컨트롤:** 버튼·입력·셀렉트 기본 높이 40px, 작은/큰 크기 32/48px를 후보로 둔다. 테이블 행·페이지네이션은 Carbon을 참고해 compact/default/comfortable을 32/40/48px로 시작한다.
- **형태:** 랜딩의 단정한 모서리를 반영해 버튼·입력 약 6px, 카드 약 8px을 출발점으로 두고 현재 토큰 값과 통합 검토한다. 배지의 pill 형태는 별도 유지한다.
- **아이콘:** 텍스트 기호·이모지 대신 크기와 선 굵기를 통일한 아이콘 규칙을 세운다. 아이콘 전용 액션에는 명확한 접근성 이름을 제공한다.
- **상태:** default, hover, focus-visible, active/selected, disabled, loading, error, empty를 기본 점검 상태로 정의한다. 키보드 탐색과 화면 너비 변화에서도 행동이 유지되어야 한다.
- **레이아웃:** 데스크톱 기준 페이지 여백 후보 24px, 작은 화면 16px. 목록·상세·폼 화면은 실제 사용 데이터의 길이와 우선순위에 맞춰 영역을 배분한다.

## 적용 범위와 순서

1. **기준 화면과 Foundation:** 현재 토큰/기본 컴포넌트의 같은 화면을 Light/Dark 및 대표 폭에서 비교하고, 색·타입·간격·높이·radius·아이콘 기준을 확정한다.
2. **기본 컨트롤:** Button, Input, Select, Checkbox, Radio, Switch, FormField를 공통 크기와 상태 규칙에 맞춘다.
3. **탐색·오버레이·피드백:** Tabs, Sidebar, Pagination, Modal, Drawer, Dropdown, Toast 등의 키보드·포커스·명암·배치를 정리한다.
4. **데이터 표시:** Table/DataTable의 역할 경계를 명확히 하고 헤더, 정렬, 검색/필터, 행 밀도, 빈 상태, 페이지네이션을 통일한다. 기능은 사용 사례가 확인된 것만 API에 추가한다.
5. **관리 템플릿:** 핵심 목록/조회와 등록/수정 흐름을 기준 화면으로 골라 실제 조합에서 기본 컴포넌트가 잘 작동하는지 확인한 뒤 나머지 템플릿을 같은 규칙으로 적용한다.
6. **Storybook과 가이드:** 단일 WindSoft 기본 테마를 첫 화면으로 두고, 테마별/상태별 예제와 통합 관리 화면, 복사 가능한 앱 코드, 토큰·조합 규칙을 정리한다.

각 단계는 하나씩 끝내며 다음 단계로 넘어가기 전에 해당 Storybook 화면과 좁은/넓은 뷰포트, Light/Dark, 키보드 동작을 검토한다. 기존 동작·API는 회귀 테스트로 보호한다.

## 제약

- React 19, Tailwind CSS 4.3.3, 기존 CSS variable + Tailwind 구성과 패키지 export 방식을 유지한다.
- 신규 의존성을 추가하지 않는다.
- 소비 프로젝트에서 쓰는 공개 props는 기존 사용을 깨지 않도록 우선 하위 호환으로 확장한다.
- 작업은 단계별 PR로 나누고, 각 단계는 문서·Storybook·검증을 함께 갱신한다.

## 승인 요청

이 제안은 기존 WindSoft 브랜드를 관리 UI의 정체성 출처로 사용하고, 데이터 밀도와 UI 동작은 Carbon/Primer를 참고해 WindSoft 규칙으로 정리하는 방향이다. 먼저 32/40/48px 크기 단계와 4px 간격 후보를 Foundation Storybook에서 시각적으로 검토한 뒤 최종 기준으로 확정한다. 이 방향과 초기 기준을 승인하면 별도의 체크 가능한 구현 계획을 작성하고 Foundation 단계부터 시작한다.
